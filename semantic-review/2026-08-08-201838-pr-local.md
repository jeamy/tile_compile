# Durable run-start claims and config revision updates (v2)

The change adds a filesystem-backed start claim so direct and queued starts cannot reuse a run ID, while preserving legacy `config.yaml` before its first claimed start. Resume and restore now require durable per-run revisions without touching that claim. Four failure boundaries remain incorrect. **Watch for:** **HIGH, likely** queue launch exceptions still escape after consuming the claim; **MEDIUM, confirmed** rejected starts replace active revision state; **MEDIUM, likely** process interruption can strand a lock or publish a claim before its config; **MEDIUM, confirmed** failed resume/restore writes leave a false selected revision.

## High-level view

Queue materialization and claim failures are converted into job errors, but the exception boundary ends before child launch. A launch failure therefore occurs after the run ID is durably consumed and can escape the detached queue task instead of producing a terminal queue job.

Start requests create and activate an in-memory config revision before attempting the per-run claim. A request rejected for an existing run ID consequently changes shared active-revision state to config that was never accepted for that run.

The lock directory and the claim/config pair are cleaned only by in-process exception handling. Process interruption can leave an unowned lock before any claim exists or leave a published claim paired with the previous `config.yaml`.

Resume and restore persist the `*_selected_config` revision before replacing `config.yaml`. If replacement fails, revision history records a selection that never became active.

1. **HIGH, likely — Queue launch exceptions escape** — `subprocess_manager.launch` runs after claim publication but outside the queue's error catches. Catch the post-claim launch path, set a terminal job error, clean staging, and explicitly resolve the consumed claim.
2. **MEDIUM, confirmed — Rejected starts activate rejected config** — Revision activation precedes collision detection, so a rejected direct or queued start changes shared active-revision state. Activate only the revision belonging to a successfully claimed start.
3. **MEDIUM, likely — Interrupted claims leave unrecoverable state** — A process exit can strand the lock directory or publish the claim before replacing `config.yaml`. Add ownership/staleness recovery and reconcile partially published claim/config transactions.
4. **MEDIUM, confirmed — Failed writes leave false selected revisions** — Resume and restore persist their selected revision before committing `config.yaml`. Commit the selected revision with the successful replacement or remove/mark it failed when replacement fails.

<details><summary>Details</summary>

## Queue launch failures bypass the job-error conversion

**HIGH, likely.** The queue catches materialization failures at `web_backend_cpp/src/routes/runs_routes.cpp:1190-1204` and claim failures at `:1207-1223`, but after the claim succeeds, `subprocess_manager.launch` runs outside either catch at `:1229-1232`; the queue lambda has no outer exception boundary through `:1267`. If launch throws, the durable claim remains and the detached queue task cannot translate the exception into `JobState::error`; the escaping thread exception can terminate the backend rather than just the queue job. Wrap the post-claim launch and monitoring path in terminal-job error handling, clean staging, and define whether a launch that never produced a child releases the claim or marks it as a failed start.

## Collision rejection mutates active revision state

**MEDIUM, confirmed.** Every request adds and activates `revision_id` at `web_backend_cpp/src/routes/runs_routes.cpp:1146-1153`, before a queue item checks its claim at `:1207-1223` and before a direct start checks at `:1277-1289`. A repeated start rejected for an existing claim therefore still sets `active_config_revision_id` to the rejected YAML; a queued collision does the same at submission and can leave that state in place until the asynchronous failure. Move revision activation after successful claim acquisition and use the accepted per-run selected revision ID, or roll the state back when the claim fails.

## Lock and claim publication are not interruption-safe

**MEDIUM, likely.** The lock is an unowned directory created at `web_backend_cpp/src/routes/runs_routes.cpp:371-376` and removed only by normal return or catch at `:377-380, :447-455`. An abrupt process exit before cleanup leaves a legacy run with no claim permanently blocked. Separately, the claim is published at `:435-440` before `config.yaml` is replaced at `:442-446`; an exit in that interval leaves a durable claim whose revision points to the new YAML while the run still exposes the old config. Use an interruption-recoverable lock with ownership/staleness validation and a recoverable transaction marker, or make startup reconcile pending claim/config state before rejecting the run ID.

## Failed config replacement leaves a false selected revision

**MEDIUM, confirmed.** Resume records `resume_selected_config` at `web_backend_cpp/src/routes/runs_routes.cpp:1704-1705` before the write checked at `:1710-1712`; restore does the same at `:1999-2000` before `:2005-2007`. If `config.yaml` cannot be replaced after the revision store succeeds, the endpoint reports failure but history says that YAML was selected even though the prior config remains active. Stage the replacement first and commit the selected revision only with the successful rename, or remove/mark the selected revision as failed when the write cannot commit.
