# Gated sharpness defaults and end-to-end run provenance

This change enables the gated affine and smooth-local registration refinements by default, switches AQMH prewarp to cubic, adds validated luma-detail transfer back into reconstructed RGB, and carries target/build/runtime identity into runs and `/api/version`. The image-processing path uses candidate-first validation and preserves prior outputs when a gate or remap fails. The provenance path adds content hashes for source, binaries, configs, and ordered inputs, while the backend now passes each runner a per-run config path instead of the mutable global config. **Watch for:** **CRITICAL, confirmed** queue snapshot failures can terminate the backend; **HIGH, confirmed** caller-selected run IDs still allow config snapshots and revision indexes to race; **HIGH, confirmed** pattern-filtered queue provenance records temporary paths that are deleted; **HIGH, confirmed** multi-config builds share generated metadata outputs; **MEDIUM, confirmed** installed runner/CLI packages omit the sidecars consumed by `/api/version`.

## High-level view

The affine, smooth-local, and RGB transfer paths are conservative at commit time. Affine and local refinements retain rollback state, failed local RGB remaps rerun every channel through the affine path, and RGB luma transfer leaves the raw R/G/B matrices untouched until both the uniform-control gates and raw-baseline guard pass.

Build metadata is generated independently for runner, CLI, and backend, and source manifests are path-sorted before hashing. Target identity is part of the build ID and runtime self-hashing avoids a circular build-time binary digest, but generated metadata is target-specific rather than configuration-specific, which races under concurrent Debug/Release builds.

Run provenance hashes the config snapshot and the ordered, post-`max_frames` input set before processing. Backend launch paths now hand the runner `<run>/config.yaml`, but that fixed path is neither exclusively reserved nor atomically immutable; queue workers also let new snapshot exceptions escape detached threads.

The version endpoint combines backend embedded metadata with hashes and sidecars for the configured CLI and runner. Build-tree layouts provide those sidecars, while `cmake --install` installs only the executables, leaving installed deployments without target build metadata.

## Queue snapshot I/O errors escape a detached thread

**CRITICAL, confirmed.** `persist_run_config_snapshot` now throws for empty YAML, directory creation failure, open failure, and final write failure (`web_backend_cpp/src/routes/runs_routes.cpp:340-374`). The queue invokes it inside `spawn_job_thread` at `runs_routes.cpp:1058-1087`, while that helper runs `task(state, job_id)` without a catch in a detached `std::thread` (`web_backend_cpp/include/routes/route_utils.hpp:152-166`). A full disk, permissions error, missing default config, or invalid run destination therefore reaches `std::terminate` and takes down the backend instead of failing one queue item. The queue task needs an outer catch that records an error job state and cleans staging, or it must use the exception-containing job wrapper.

## Fixed per-run config paths are mutable under run-ID collisions

**HIGH, confirmed.** Every start truncates `<runs_dir>/<run_id>/config.yaml` in place (`runs_routes.cpp:340-374`) and custom run IDs are accepted without exclusive directory reservation. Two direct starts, two queues, or a queue and direct start that derive the same run ID can overwrite the same file while both children receive that same pathname (`runs_routes.cpp:1086-1102, 1149-1156`). The disk revision helpers are also lock-free read/modify/write operations, so concurrent writers can select the same second-based revision ID and lose index entries (`web_backend_cpp/src/services/config_revisions.cpp:168-198`).

The runner loads the config first (`tile_compile_cpp/apps/runner_pipeline.cpp:1133`) and only later copies or self-detects the snapshot and hashes it (`runner_pipeline.cpp:1176-1194`). A colliding writer in that interval can make the parsed effective configuration differ from `config.yaml`, its provenance SHA-256, and the revision history. Reserve run IDs atomically, reject reuse by new runs, write a uniquely named snapshot via temporary-file-plus-rename, and parse/hash the exact captured bytes rather than reopening a mutable path.

## Queue manifests retain paths that cleanup removes

**HIGH, confirmed.** Patterned queue inputs are symlinked or copied under `.queue_staging/<job>/item_N` and that staged directory is passed to the runner (`runs_routes.cpp:618-640, 1097-1102`). Provenance stores `fs::absolute(path)` rather than resolving the source identity (`tile_compile_cpp/apps/runner_pipeline.cpp:91-107`), then queue completion, cancellation, and failure all remove the staging root (`runs_routes.cpp:1069, 1127, 1138`). The content hashes remain, but every recorded entry path becomes dead; when symlink creation fell back to copying, the manifest cannot recover the original source path at all. Record canonical source paths or an explicit source-to-staged mapping before launch, and keep the digest defined over that durable identity.

## Multi-config builds race on one generated header and JSON file

**HIGH, confirmed.** `tile_compile_add_build_info` writes one target-level directory, header, and JSON sidecar regardless of configuration (`cmake/TileCompileBuildInfo.cmake:17-19`), while the generated contents include `$<CONFIG>` (`TileCompileBuildInfo.cmake:24-43`). Concurrent Debug and Release builds for Visual Studio, Xcode, or Ninja Multi-Config can overwrite the same header while the other configuration compiles and can copy the other configuration's JSON in its post-build step (`TileCompileBuildInfo.cmake:48-54`). This can produce a binary and sidecar that disagree or report the wrong build type. Put `$<CONFIG>` in the generated directory/output identity and wire each configuration to its own header and sidecar.

## Installed executables lose their target build-info sidecars

**MEDIUM, confirmed.** Build targets copy `${target}.build-info.json` beside each executable (`cmake/TileCompileBuildInfo.cmake:51-54`), and `/api/version` only loads target metadata from that adjacent file (`web_backend_cpp/src/routes/system_routes.cpp:37-50`). The install rule installs `tile_compile_runner` and `tile_compile_cli` but not either sidecar (`tile_compile_cpp/CMakeLists.txt:660-664`). In an installed layout, `/api/version` can still hash an executable resolved by absolute path, but its `build_info` is `null`, defeating the target-specific source/toolchain portion of the endpoint. Install the generated sidecars next to the runtime targets, or obtain embedded JSON from each executable instead of relying on a build-tree artifact.

## Atomic refinement and RGB transfer commits

The RGB transfer builds candidate channel matrices separately and moves all three into the result only after `evaluate_aqmh_validation_gates(...).all_ok` and `aqmh_raw_baseline_guard_decision(...).ok` (`tile_compile_cpp/apps/runner_phase_aqmh_reconstruction.cpp:1210-1282`). Numerical failure and either quality rejection leave the original channel matrices in place. Registration snapshots each frame's warp and aggregate counters before refinement, restores them on exceptions, invalidates rejected local models, and reprocesses all three RGB channels through affine prewarp if any local remap fails (`tile_compile_cpp/apps/runner_phase_registration.cpp:3730-3985, 4350-4405`).
